# B2: scheduled batches and CPU prefetch

B2 addressed the costs left by [B1](b1.md): NVARC padded 16 different-length
sources to one shared length, and FLUX still needed 48 separate calls per
optimizer step. B2 split the NVARC window into smaller groups, combined FLUX
targets into larger batches, and prepared upcoming inputs in CPU workers.
The VAE still processed all 48 target images in one batch per optimizer step.

Across all measured steps, B2 reached **4.201 targets/s**, with a median
optimizer step of **11.32 s**: **21.4% more throughput than B1**. Each update
still used the same 48 targets in the same logical order.

The [benchmark overview](README.md) explains the shared dataset, hardware,
measurement protocol, and comparison across variants.

## How B2 ran

B2 used the same 960 augmented sources and three eligible targets per source
as B0 and B1. NVARC and the VAE stayed frozen; the complete FLUX transformer
was trainable. Two schedulers chose physical batches without changing which
targets contributed to an optimizer update.

1. Read the next 16 sources in their recorded order. Two CPU workers loaded,
   augmented, formatted, and tokenized upcoming sources in the background.
2. Group eligible sources by length into NVARC batches of two, four, or eight.
   Pad each group to a length from the NVARC catalog, mask the padding, and
   run each group separately. Keep only the real hidden-state positions.
3. Restore source order and create the target examples. Encode the 48 target
   images in one VAE call, independently of the smaller NVARC groups.
4. Append the examples to the FIFO queue and select its next 48 targets for
   one optimizer update. Assign noise and timesteps in that logical order.
5. Group those selected targets into FLUX microbatches of one, two, or four,
   using the measured forward/backward times in the FLUX catalog. Pad and
   mask each group's text prefixes; keep 900 image tokens per target.
6. Run forward and backward for each group. A group of `m` targets contributes
   `mean_loss * m / 48`, so every target has the same weight regardless of
   its physical group size. A smaller final optimizer batch uses its actual
   target count as the denominator.
7. Apply one optimizer update and release gradients before the next frozen
   NVARC/VAE preparation phase.

NVARC regrouping stayed inside the 16-source window. FLUX regrouping stayed
inside the selected optimizer batch, and the sampled noise and timesteps
followed their targets. Neither scheduler pulled in targets from later steps.

Releasing gradients after the update freed memory for preparation. An earlier
B2 run had kept them alive through that phase and encountered cuDNN workspace
warnings. In the reported benchmark, gradients were freed immediately after
each optimizer update. They still remained resident between FLUX microbatches
during accumulation.

### Run parameters

| Parameter | B2 value |
| --- | --- |
| NVARC preparation window | 16 consecutive sources |
| NVARC physical batch size | 2, 4, or 8 sources from the window; one exact-length singleton for an odd eligible-source count |
| VAE microbatch size | 48 target images per call |
| FLUX microbatch size | 1, 2, or 4 targets, selected from the measured catalog |
| Optimizer batch size | 48 targets, accumulated across the selected FLUX groups |
| Length policy | Separate NVARC and FLUX shape catalogs; masked padding |
| Input order | FIFO optimizer membership; physical grouping may reorder sources or targets within a window |
| DataLoader workers | 2, with ordered delivery and `prefetch_factor=8` |
| Precision | Frozen NVARC in BF16; frozen VAE in FP32; FLUX parameters in FP32 with BF16 compute |
| Activation checkpointing | Disabled |

<details>
<summary>NVARC batch selection and bucket boundaries</summary>

<p>The NVARC catalog used the source lengths recorded in B0's 60 windows of
16 sources. B2 grouped similar lengths so that a few long sources would not
force the whole window to use a large padding length. Boundaries were chosen
for each batch size from the observed distribution.</p>

<pre>Sources per call | Available text boundaries
2                | 864, 3022, 4250, 6010, 6870, 8400
4                | 1083, 1431, 1718, 2190, 2824, 3122,
                 | 3372, 3780, 4204, 4507, 4836, 5380
8                | 2528, 2702</pre>

<p>Each boundary belongs only to the batch size in its row. The scheduler
sorted sources by descending length and used dynamic programming to choose
consecutive groups. Its cost was the sum of batch size times padded length,
plus 2,560 per call. The call penalty discouraged too many small batches;
it was a token-count heuristic, not a measured GPU latency.</p>

<p>An odd number of eligible sources used one exact-length singleton. This
covered short tails without dropping sources or padding with dummy examples.
The catalog was fitted to the benchmark subset; it was not established as
optimal on the full training dataset.</p>

</details>

<details>
<summary>FLUX shape measurements and batch selection</summary>

<p>FLUX needed measured memory and timing limits: longer text prefixes left
room for fewer targets in one call. The H200 probe tested 16 candidate text
boundaries with batch sizes one, two, four, and eight. It used synthetic
near-boundary inputs with masked padding, two warm-up calls, and five measured
calls per shape.</p>

<p>The frozen models, FLUX gradients, optimizer state, and a 1.964 GiB
preparation reserve stayed resident. This modeled later accumulation calls,
where gradients already occupy memory. The probe recorded 39 passing shapes,
15 OOMs, and 10 larger shapes skipped after an OOM at the same length.
Skipped shapes were not measured failures.</p>

<pre>Text boundary                          | Largest passing batch
487                                    | 8
778, 1090, 1348, 1578, 1818, 2126, 2422 | 4
2749, 2990, 3325, 3714, 4210, 4837      | 2
6100, 8400                             | 1</pre>

<p>We excluded the 2,422-token batch of four because its 133.20 GiB peak
allocation left only 6.60 GiB below device capacity. The 487-token batch of
eight was also excluded: it was selected only four times across the replayed
windows and saved about 3 ms per step in the cost model. Removing shapes
with little predicted benefit reduced the remaining 37 shapes to this
24-shape catalog:</p>

<pre>Targets per call | Available text boundaries
4                | 487, 778, 1090, 1348, 1578, 1818, 2126
2                | 487, 1348, 2126, 2422, 2749, 2990, 3325,
                 | 3714, 4210, 4837
1                | 487, 2422, 3325, 4210, 4837, 6100, 8400</pre>

<p>Retained shapes peaked at at most 127.90 GiB allocated in the probe.
That margin was an observation, not a guarantee for every training allocation
history. Replaying the 60 windows predicted 9.492 s of FLUX forward/backward
work per step, versus 10.678 s for singletons at the candidate boundaries.
These were estimates from isolated shape timings, not measured complete steps.</p>

<p>The FLUX scheduler sorted the selected targets by descending prefix length
and used dynamic programming to minimize the sum of configured whole-call
times. It could accept more padding if a larger batch was faster overall.
Unlike NVARC's token-count penalty, this cost came from GPU measurements.
Singleton catalog entries covered partial groups. The original probe report
retains the full protocol and per-shape evidence.</p>

</details>

## Benchmark result

Each run started with ten warm-up steps before timing the next 50 steps.
The warm-up steps are excluded from the timing results. All three runs used
the same inputs on one H200.

| Run | Median step | p95 step | Targets/s | Peak allocated | Peak reserved |
| --- | ---: | ---: | ---: | ---: | ---: |
| Run 1 | 11.27 s | 13.49 s | 4.206 | 126.48 GiB | 133.06 GiB |
| Run 2 | 11.33 s | 13.34 s | 4.197 | 126.48 GiB | 133.06 GiB |
| Run 3 | 11.37 s | 13.46 s | 4.199 | 126.48 GiB | 133.06 GiB |
| **Median of the three runs** | **11.33 s** | **13.46 s** | **4.199** | **126.48 GiB** | **133.06 GiB** |
| B2: all 150 measured steps combined | 11.32 s | 13.47 s | 4.201 | 126.48 GiB | 133.06 GiB |
| [B1](b1.md): all 150 measured steps combined | 13.91 s | 15.77 s | 3.461 | 113.90 GiB | 118.84 GiB |
| [B0](b0.md): all 150 measured steps combined | 15.45 s | 17.59 s | 3.094 | 113.91 GiB | 138.12 GiB |

B2 delivered **21.4% more targets/s than B1** and **35.8% more than B0**,
with higher peak allocated memory.

The measured batch counts show how the work changed:

| Work per optimizer step | B1 | B2 |
| --- | ---: | ---: |
| Mean NVARC calls | 1.00 | 4.14 |
| NVARC padded / real token positions | 2.14x | 1.22x |
| Mean FLUX microbatches | 48.00 | 18.68 |
| FLUX text padding above real positions | 7.88% | 10.14% |

NVARC processed 42.8% fewer padded positions, while FLUX needed 61.1% fewer
calls and accepted slightly more text padding. These counts cover the 50
measured steps per run; they are not runtime speedup percentages.

## What the profiler showed

B2 reduced NVARC's padded work and the number of FLUX calls. The profiler
showed shorter total ranges for both models, while some gaps remained.

**This trace was recorded before we started freeing FLUX gradients immediately
after each optimizer update.** The benchmark results above already include
that change. In this older trace, the gradients still occupied GPU memory
during NVARC/VAE preparation.
The table reports seconds per optimizer step over three active profiler
steps. Changes use unrounded totals.

| Phase | Activity B1 | Activity B2 | Gaps B1 | Gaps B2 | Total B1 | Total B2 | Change total |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| NVARC | 2.198 | 1.081 | 0.016 | 0.355 | 2.214 | 1.436 | -35.1% |
| VAE | 0.374 | 0.390 | 0.001 | 0.051 | 0.375 | 0.440 | +17.4% |
| FLUX forward | 2.824 | 2.674 | 0.409 | 0.198 | 3.233 | 2.872 | -11.2% |
| FLUX backward (reconstructed) | 6.380 | 5.325 | 0.323 | 0.629 | 6.702 | 5.954 | -11.2% |

**NVARC: less padding, more calls.** GPU activity fell by 50.8%, from 2.20 to
1.08 s per step. The three profiled steps used 11 NVARC calls instead of
three. Larger gaps offset part of the saved work, leaving a 35.1% shorter
total range. Five attention calls still exceeded 20 ms, compared with none
in B1, consistent with some remaining setup work.

**FLUX: fewer forward/backward calls.** Each pass made 1,300 attention calls
across the active window, down from 3,600 in B1. Forward activity decreased
and its gaps roughly halved. Backward activity also decreased, but its gaps
grew. Both total ranges fell by 11.2%. Eight attention calls per pass exceeded
20 ms, versus two in B1, so fewer calls did not remove every setup cost.

**VAE: the same batch, but memory pressure in the older trace.** The VAE still
encoded 48 images per call. Its range grew by 17.4%, with extra allocation
and plan-retry gaps consistent with the workspace warnings. These observations
come from the run that still held FLUX gradients in memory during preparation;
they do not show how the VAE performed after those gradients were freed earlier.

**CPU preparation: work moved into background workers.** Retrieving the 16
sources took 0.009 s per step, down from 0.171 s in B1. Workers still did the
loading and tokenization; the main process spent less time retrieving inputs.
These CPU ranges do not measure GPU idle time or the isolated prefetch gain.

The table covers GPU phase ranges, not complete optimizer-step times.
Backward ranges were reconstructed from GPU activity. The profiler averaged
17.33 FLUX microbatches per step versus 18.68 in the benchmark, so its phase
changes should not be treated as a breakdown of the full run.

<details>
<summary>Prepared follow-up: FLUX alignment</summary>

<p>The irregular catalog boundaries raised another question: would rounding
them to hardware-friendly multiples improve the padded FLUX path? The plan
compared each shape with text lengths or joint text-plus-image lengths rounded
up to multiples of 8, 32, 64, and 128, keeping real inputs, batch size, noise,
and timesteps fixed.</p>

<p>For example, 2,422 text tokens become 2,432 when aligning text to 32, or
2,428 when aligning the joint sequence after adding 900 image tokens.
The plan contained 140 physical cases across the 24 catalog shapes.
The historical alignment report contains no H200 measurement result, and
this experiment did not change the B2 catalog.</p>

</details>

## Next step: B3

We first investigated whether better-aligned padding lengths could make the
B2 batches faster. The [NVARC alignment tests](https://github.com/joshuakauling/diffusion-arc/blob/271be103ded3599eafe268606f26357391a8bf78/docs/performance/nvarc-batch-shapes.md) improved
some shapes, but did not produce a generally better rounding rule. The
corresponding FLUX experiment was prepared but has no reported GPU result.

We then expanded the investigation to other attention backends. The first
[NVARC comparison](https://github.com/joshuakauling/diffusion-arc/blob/271be103ded3599eafe268606f26357391a8bf78/docs/performance/nvarc-packing.md#comparison-with-the-previous-implementation)
tested FA2 with the existing B2 groups, followed by FA2 with unpadded packing.
Variable-length attention opened up a different approach: process sequences
together without padding them to a shared length, while keeping their
attention boundaries separate.

That shifted the focus from improving the padding catalogs to replacing them
with sequence packing. Further backend comparisons led to FA3 for B3. NVARC
could process a whole source window in one call; FLUX could group exact
text-plus-image sequences under a token budget. For FLUX training, this also
required checking forward and backward behavior and investigating gradient
differences. Those experiments are covered in the B3 component reports.
