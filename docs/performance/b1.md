# B1: fixed buckets and batched preparation

B1 addressed the setup gaps seen in [B0](b0.md). Instead of using a different
attention shape for every exact text length, it padded inputs to a small set
of shared lengths, called buckets. For each optimizer step, it prepared
one NVARC batch of 16 sources and one VAE batch of their 48 target images.

Across all measured steps, B1 reached **3.461 targets/s**, with a median
optimizer step of **13.91 s**: **11.9% more throughput than B0**. FLUX still
processed one target at a time and accumulated 48 targets per optimizer update.

The [benchmark overview](README.md) explains the shared dataset, hardware,
measurement protocol, and comparison across variants.

## How B1 ran

B1 used the same 960 augmented sources and the same three eligible targets
per source as B0. NVARC and the VAE stayed frozen, and the complete FLUX
transformer was trainable. Source order, optimizer targets, and loss weights
stayed the same.

1. Load and tokenize the next 16 sources in their recorded order.
2. Find the longest consumed source prefix and round it up to the next NVARC
   bucket. Pad all 16 sources to that length, mask the padding, and run NVARC
   once. Keep only each source's real hidden-state positions.
3. Create the 48 target examples from their respective conditioning prefixes.
   Render their target grids and encode all 48 images in one VAE call.
4. Place the examples in the FIFO queue and select the next 48 targets for
   one optimizer update.
5. Run FLUX on each target separately. Round its text prefix up to the next
   FLUX bucket and mask the added padding. The 900 image tokens stay unchanged.
   Backpropagate each target's flow-matching loss with weight `1 / 48`.
6. Apply one optimizer update after all 48 forward/backward calls.

NVARC used seven bucket lengths and FLUX used 19. For example, FLUX padded
both a 454-token and a 468-token prefix to 512 text tokens. Both calls then
had the same joint length of 1,412 tokens and could reuse attention plans.
The real prefixes stayed intact; the added positions were masked.

### Run parameters

| Parameter | B1 value |
| --- | --- |
| NVARC source batch size | 16 sources per call |
| VAE microbatch size | 48 target images per call |
| FLUX microbatch size | 1 target per forward/backward call |
| Optimizer batch size | 48 targets, accumulated over 48 calls |
| Length policy | Seven NVARC buckets and 19 FLUX text buckets; masked padding |
| Input order | FIFO; no loader shuffle or length-based reordering |
| DataLoader workers | 0; data preparation in the main process |
| Precision | Frozen NVARC in BF16; frozen VAE in FP32; FLUX parameters in FP32 with BF16 compute |
| Activation checkpointing | Disabled |

## Benchmark result

Each run started with ten warm-up steps before timing the next 50 steps.
The warm-up steps are excluded from the timing results. All three runs used
the same inputs on one H200.

| Run | Median step | p95 step | Targets/s | Peak allocated | Peak reserved |
| --- | ---: | ---: | ---: | ---: | ---: |
| Run 1 | 13.90 s | 15.75 s | 3.465 | 113.90 GiB | 118.84 GiB |
| Run 2 | 13.93 s | 15.77 s | 3.460 | 113.90 GiB | 118.84 GiB |
| Run 3 | 13.93 s | 15.77 s | 3.460 | 113.90 GiB | 118.84 GiB |
| **Median of the three runs** | **13.93 s** | **15.77 s** | **3.460** | **113.90 GiB** | **118.84 GiB** |
| All 150 measured steps combined | 13.91 s | 15.77 s | 3.461 | 113.90 GiB | 118.84 GiB |

The 11.9% throughput gain includes both bucket padding and larger preparation
batches. Their individual contributions were not measured separately.

## What the profiler showed

B1 largely removed the attention-setup gaps seen in B0. FLUX and the VAE
became faster, but NVARC spent more time processing padded sources.

The table separates recorded GPU activity from gaps between operations.
Together they form each phase's total GPU range. Values are seconds per
optimizer step, averaged over the three active profiler steps. Changes use
unrounded totals, so rounded columns may not add up exactly.

| Phase | Activity B0 | Activity B1 | Gaps B0 | Gaps B1 | Total B0 | Total B1 | Change total |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| NVARC | 0.698 | 2.198 | 0.743 | 0.016 | 1.440 | 2.214 | +53.7% |
| VAE | 0.632 | 0.374 | 0.030 | 0.001 | 0.662 | 0.375 | -43.4% |
| FLUX forward | 2.657 | 2.824 | 3.400 | 0.409 | 6.057 | 3.233 | -46.6% |
| FLUX backward (reconstructed) | 6.013 | 6.380 | 2.910 | 0.323 | 8.923 | 6.702 | -24.9% |

**NVARC: less waiting, more padded work.** Its gaps almost disappeared, but
GPU activity rose from 0.70 to 2.20 s per step. Padding all 16 sources to one
bucket meant processing 2.14 times as many positions as real tokens across
the measured benchmark steps; in the shorter profiler window, the ratio was
2.26. The total NVARC range grew by 53.7%.

Mixed-length batches also changed NVARC's attention execution. Transformers
built an explicit mask and repeated the key/value heads instead of using
native grouped-query attention. The trace did not separate those costs from
the extra padded positions. Changing mask values alone did not require a
new attention plan when the shape stayed the same.

**VAE: fewer, larger calls.** Encoding 48 images together reduced GPU activity
from 0.63 to 0.37 s per step. With almost no gaps left, the total VAE range
fell by 43.4%.

**FLUX: shape reuse outweighed the extra padding.** Forward and backward both
showed slightly more GPU activity, consistent with the added text padding.
Their gaps shrank much more: forward fell from 6.06 to 3.23 s in total, and
backward from 8.92 to 6.70 s. The isolated cost of padding was not measured.

The attention-call counts support plan reuse as the explanation. The backend
remained cuDNN, and FLUX made the same number of calls. Calls longer than
20 ms almost disappeared:

| Attention calls across all three active steps | B0 total | B0 long | B1 total | B1 long |
| --- | ---: | ---: | ---: | ---: |
| FLUX forward | 3,600 | 256 | 3,600 | 2 |
| FLUX backward | 3,600 | 256 | 3,600 | 2 |
| NVARC forward | 1,728 | 45 | 108 | 0 |

These are CPU attention calls. Their durations overlap GPU execution, so
they cannot be added to the table above as extra time savings.

The profiler captured three early steps, where B0 encountered more new shapes
than over the full benchmark: 88.9% of forwards used a new length, compared
with 62.0% during benchmark measurement. B1 had already used 16 of its 19
FLUX buckets before profiling; only the 256-token bucket was new during the
active window. This explains why the large early phase improvements do not
translate into the same percentage gain for the complete benchmark.

CPU data loading still fetched the 16 sources synchronously before NVARC,
taking 0.171 s per step. This identified another opportunity for B2 to prepare
inputs in background workers; the CPU range alone does not measure GPU idle time.

The table covers GPU phase ranges from three profiled steps, not complete
optimizer-step times. Backward ranges were reconstructed from GPU activity.

## Next step: B2

To reduce the NVARC padding, [B2](b2.md) split each 16-source window into
smaller groups of similar lengths. The VAE could still encode the window's
48 target images together, independently of those NVARC groups.

FLUX still required 48 separate calls per update in B1. B2 therefore measured
which larger FLUX batches fit in memory and used those timings to group
targets within each optimizer batch. It also moved CPU data preparation into
background workers. Target membership and per-target loss weights stayed fixed.
