# B0: first end-to-end training run

B0 was the first simple version of the complete training pipeline. The goal
was to implement the data flow and test it in training with the real models:
load and augment ARC data, encode it with NVARC, turn the hidden states into
individual FLUX examples, and train the FLUX transformer.

The initial approach kept execution simple. NVARC processed each source
separately, and the VAE and FLUX processed each target separately. There was
no sequence padding or grouping of examples within a model call. Gradients
from 48 individual FLUX targets accumulated before each optimizer update.
Across all measured steps, B0 reached **3.094 targets/s**, with a median
optimizer step of **15.45 s**.

This became the reference for later batching optimizations. The
[benchmark overview](README.md) explains the benchmark setup, shared dataset,
hardware, measurement protocol, and comparison across variants.

## How B0 ran

The benchmark used 960 sources, each with five input/output pairs. The first
two pairs provided context, leaving three eligible training targets. NVARC
and the VAE were frozen; the complete FLUX transformer was trainable.

1. Load the selected ARC task and apply its recorded augmentation. This
   benchmark used a random color permutation and unchanged geometry. Format
   the pairs as an ARC prompt and tokenize it for NVARC.
2. Run NVARC on one source, stopping the input before the final target output.
   Collect hidden states from layers 9, 18, and 27 and concatenate their
   features. All three targets share these source states.
3. Create one FLUX example per eligible target. Each example selects only the
   hidden-state prefix before its own output, so it cannot see that output or
   later pairs. Render its target grid and encode the image separately with
   the VAE into 900 image tokens.
4. Place the prepared examples in a FIFO queue: first in, first out. The next
   48 targets form one optimizer batch, keeping source and target order.
5. Process those targets one at a time through FLUX. Each call receives the
   exact conditioning prefix and noisy image latents for that target. Compute
   the flow-matching loss and backpropagate it with weight `1 / 48`.
6. Apply one AdamW update after all 48 forward/backward calls.

The physical batch size was one throughout. The optimizer batch size was 48,
implemented through gradient accumulation. No length buckets or length-based
reordering were involved. This made the data flow straightforward, but required
many separate calls with different attention shapes.

### Run parameters

| Parameter | B0 value |
| --- | --- |
| NVARC source batch size | 1 source per call |
| VAE microbatch size | 1 target image per call |
| FLUX microbatch size | 1 target per forward/backward call |
| Optimizer batch size | 48 targets, accumulated over 48 calls |
| Input order | FIFO; no loader shuffle or length-based reordering |
| DataLoader workers | 0; data preparation in the main process |
| Precision | Frozen NVARC in BF16; frozen VAE in FP32; FLUX parameters in FP32 with BF16 compute |
| Activation checkpointing | Disabled |

## Benchmark result

Each run started with ten warm-up steps to let the pipeline warm up before
timing the next 50 steps. The warm-up steps are excluded from the timing
results. All three runs used the same inputs on one H200.

| Run | Median step | p95 step | Targets/s | Peak allocated | Peak reserved |
| --- | ---: | ---: | ---: | ---: | ---: |
| Run 1 | 15.53 s | 17.41 s | 3.089 | 113.91 GiB | 138.12 GiB |
| Run 2 | 15.38 s | 17.52 s | 3.104 | 113.91 GiB | 138.12 GiB |
| Run 3 | 15.49 s | 17.59 s | 3.089 | 113.91 GiB | 138.12 GiB |
| **Median of the three runs** | **15.49 s** | **17.52 s** | **3.089** | **113.91 GiB** | **138.12 GiB** |
| All 150 measured steps combined | 15.45 s | 17.59 s | 3.094 | 113.91 GiB | 138.12 GiB |

## What the profiler showed

The trace below shows three consecutive FLUX forwards. The GPU timeline at
the bottom has large gaps in the first and third forwards. The middle forward
is much more compact.

![B0 cuDNN attention-plan setup](assets/b0-cudnn-attention-plan-cache.png)

The gaps line up with long cuDNN attention calls on the CPU. The red and
orange annotations mark the first attention call in the double-stream and
single-stream blocks. Each block type uses a different tensor layout and
needs its own attention setup.

The pattern points to cuDNN execution-plan setup: preparing how to run attention
for a particular shape, then caching that plan for reuse. The 454- and
770-token prefixes introduced new shapes. The 612-token shape had already
appeared, so both setup sections were much shorter and the GPU work ran
closer together.

The timings show the same pattern:

| Text tokens | Seen before? | FLUX GPU range | Recorded GPU activity | Gaps |
| ---: | --- | ---: | ---: | ---: |
| 454 | No | 119.9 ms | 31.2 ms | 88.7 ms |
| 612 | Yes | 48.4 ms | 34.5 ms | 13.9 ms |
| 770 | No | 127.3 ms | 37.0 ms | 90.3 ms |

The 612-token forward performed slightly more GPU work than the 454-token
forward, but its gaps fell from 88.7 to 13.9 ms. Reusing the shape reduced the
time between operations, rather than the amount of attention computation.

## Next step: B1

To tackle this setup cost, [B1](b1.md) introduced fixed length buckets for
NVARC and padded FLUX text prefixes to a small set of predefined lengths.
Different real lengths could then share an attention shape and reuse its
cached plans. Added padding was masked so it could not affect real tokens.

B1 also processed 16 NVARC sources together and encoded their 48 target images
in one VAE batch. The next benchmark tested whether shape reuse and fewer
preparation calls outweighed the extra work from padding.
